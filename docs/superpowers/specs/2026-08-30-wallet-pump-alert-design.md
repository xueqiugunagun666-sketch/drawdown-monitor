# 钱包暴涨异动报警 —— 设计

日期：2026-08-30
状态：待实现

## 1. 要解决的问题

用户在多条链上持有很多代币，某个币暴涨时注意不到。需要一个自动发现持仓、
监控价格、在暴涨时用声音叫醒用户的功能，集成进现有的回撤监控站点。

**只做暴涨，不做暴跌。** 暴跌有别的渠道看（"捡垃圾频道"），且现有的回撤
报警已经覆盖了下跌方向。

## 2. 硬约束（沿用项目既有的五条）

1. 所有价格计算用 `decimal.js`，禁止用 JS number 做价格算术。余额同理 ——
   ERC20 余额是 256 位整数，`Number` 在 2^53 就失真，必须全程字符串/Decimal。
2. 密钥掩码：RPC 端点是用户的私有基础设施，按密钥处理 —— 只从 env 读，
   注册进掩码表，日志与前端响应里一律掩码。
3. 不实现任何交易/下单功能。本功能只读链上数据。
4. 静默失效比误报危险：扫描失败、RPC 不可用、钱包长时间没扫成、声音权限
   未授权，全部要在 UI 上显式暴露。
5. 不要过度设计。

## 3. 范围

**做：** Ethereum / BSC / Base / Robinhood(4663) 四条 EVM 链。

**不做：** Solana（用户决定暂缓）。公共节点全部封禁了
`getTokenAccountsByOwner`（实测 publicnode 返回 `Request blocked`，
drpc 返回 `not available on free plan`），需要额外申请带 key 的服务，
本期不引入这个依赖。

**不做：** Telegram 推送。每个人持仓不同，群发没有意义。只做网页声音报警。

## 4. 身份与隔离

### 4.1 现状问题

站点目前只有一个共享的 `ACCESS_TOKEN`（`src/middleware.ts`），10 个人用同一个。
`display_name` cookie 是自己填的署名，不是身份（`src/lib/user.ts` 的注释里
已经写明"理论上能冒充他人"）。因此**在现有架构下无法做到"互不查看持仓"**。

### 4.2 方案

引入轻量用户系统。**不替换**现有的 `ACCESS_TOKEN`，而是叠加在它之上：
进站仍然要共享口令，钱包区再要求一次个人登录。

- `users` 表：用户名 + scrypt 密码哈希。scrypt 用 Node 内置 `crypto`，不加依赖。
- 会话：随机 token 存 httpOnly cookie，**库里只存哈希**。
- 钱包、持仓、报警记录全部按 `user_id` 隔离。任何钱包相关的 API 都必须
  从会话推导 `user_id`，**绝不接受请求参数里传来的 user_id**。

注意边界：这防得住彼此（他们没有对方的密码），防不住能登服务器读 SQLite 的人。

## 5. 采集层

### 5.1 端点

四条链共用一个 RPC 代理，路径里是 chain id：`${EVM_RPC_BASE}/{chainId}`。
`EVM_RPC_BASE` 从 env 读，按密钥掩码。实测四条链全部可达：

| chainId | 链 | 块高（实测时） |
|---|---|---|
| 1 | Ethereum | 25,867,277 |
| 56 | BSC | 118,937,890 |
| 8453 | Base | 50,646,913 |
| 4663 | Robinhood | 49,913,278 |

### 5.2 发现持仓

`eth_getLogs`，`topics = [Transfer, null, padded(钱包地址)]`，即"这个地址收过
哪些代币"。对结果按 `log.address` 去重，得到候选代币合约列表。

**实测**：Robinhood 链 `fromBlock=0 → latest` 一次查完，1,076 条日志 /
30 个代币 / 4.5 秒。地址过滤让结果集变得很小，不需要按块分片。

**限制是响应体积，不是块跨度。** 极度活跃的地址（拿 vitalik.eth 压测）会返回
`Log response size exceeded`。因此需要**自适应二分**：全范围失败就把区间对半
拆开递归，直到每段都能返回。普通钱包一次到位，极端地址多几次。

**增量**：每个钱包记 `last_scanned_block`，之后只扫新块。首次之后近乎免费。

**为什么这样够用**：你不可能持有一个从未收到过的代币，所以"收过"是"持有"的
超集。用当前 `balanceOf` 把卖掉的筛掉即可。

### 5.3 读余额

对发现的代币合约读 `balanceOf`，用 **JSON-RPC 批量请求**（一个 HTTP 请求里发一个
调用数组），不用 Multicall3。

实测已验证：BSC 上一次批量发三个 `eth_call`，WBNB 余额、CAKE 余额、WBNB decimals
全部正确返回。调用数据是手写的 4 字节选择器加 32 字节左补零地址：

```
balanceOf(address) = 0x70a08231 + 地址左补零到 32 字节
decimals()         = 0x313ce567
```

**为什么不用 Multicall3**：它需要对 `(address,bool,bytes)[]` 这种嵌套动态类型做
ABI 编码，项目里没有 viem/ethers，手写容易错；引入编码库又是新依赖。
JSON-RPC 批量拿到了同样的"一次往返读很多个"的收益，代价是十行代码，
而且不依赖任何合约在链上部署——Robinhood 这种新链本来就未必有 Multicall3。

每批 50 个调用，超出就分批。

余额是 uint256，**全程按十进制字符串处理**，配合 `decimals` 换算成人类数量时
用 Decimal，不经过 Number（`Number` 在 2^53 就失真，而 18 位小数的代币余额
轻易超过它）。

### 5.4 频率

10–15 分钟扫一次。余额变化远比价格慢，更密没有收益。

## 6. 过滤层

**这一层是生死线，不是优化项。** 实测拿 vitalik.eth 查 Blockscout，返回
**7,984 个代币，其中只有 368 个有价格**。不过滤，系统当场被压垮。

过滤发生在"进入监控"之前，不是报警时才滤。顺序：

1. `balanceOf > 0`
2. DexScreener 查得到主池（查不到就没有可信价格）
3. 流动性 ≥ $5,000 **且** 24h 成交量 ≥ $10,000

第 3 条两个条件必须同时卡：空投垃圾币经常有假池子撑流动性但几乎零真实成交，
只卡流动性拦不住。

阈值上线后可在页面调整，这里是默认值。

**必须有滞回**，否则一个恰好卡在 $5,000 流动性附近的币会反复进出监控集，
每次重新进入都触发一次冷启动 seed，状态被反复重置。规则：进入监控要求
达到门槛，退出监控要求跌破门槛的 60%（即 $3,000 / $6,000）且持续 30 分钟。

**被过滤掉的币要在 UI 上可见**，带上原因（第 4 条铁律）。用户需要能看出
"我这个币为什么没被监控"，而不是它静静消失。

## 7. 异动引擎

### 7.1 判定

固定倍数阈值，不是波动率分位数。

- **窗口**：5m / 1h / 6h / 24h，四个同时判
- **基准**：两个都算 —— 窗口内最低点、窗口起点价格。报警消息里标明是哪种
- **档位**：2x / 5x / 10x，每档各报一次。**`2x` 指现价是基准价的 2 倍（即 +100%）**，
  不是 +200%

四个窗口都在 5m candle 序列上求值，含当前那根未收盘的 candle：
"窗口最低点"取窗口内所有 candle 的 `l` 的最小值，"窗口起点"取最老那根的 `o`。
5m 窗口因此就是当前这一根 candle 自身的 `l` 与 `o`。

5 分钟窗口 + 从低点算，在薄盘币上极易触发（一笔两千块的买单打穿深度就够）。
流动性门槛是这套里唯一的刹车，这是它必须有效的原因。

### 7.2 状态机

**全局的，不按用户。** 价格变动是全局事实，只有"通知谁"是每人不同的。
键为 `(token_id, window, basis, level)`，复用现有 ARMED/FIRED 机制
（`src/worker/stateMachine.ts`）。触发后扇出给所有持有该币的用户。

这个设计顺带解决了一个边界情况：用户 B 新加的钱包持有一个已经涨到 2x
且状态已是 FIRED 的币 —— 状态机不会重复触发，B 自然不会收到追溯报警。

### 7.3 冷启动

**一个币首次进入监控时必须 seed 状态，不追溯补报。** 若它此刻已经在 5x，
把 2x 和 5x 两档直接置为 FIRED，只有涨到 10x 才响。

这是已经踩过的坑的同一个机制：之前"新加入的代币若已跌破阈值会连推 75/80/85"
（commit `6699db0`），修法是 `seedState()`。暴涨方向必须做同样的事。

### 7.4 去重

同一个币的一波行情会让多个窗口先后达标（5m 先中，1h 随后，24h 再中）。

规则要写死，否则实现时必然各写各的：**同一个币在 30 分钟内，只发出倍数最高的
那一条报警。** 具体做法是把触发攒在一个 30 分钟的窗口里，取 `multiple` 最大的
一条发出，其余的状态照常置 FIRED 但不产生通知（状态必须置，否则窗口过后会重放）。

倍数相同时，取窗口更短的那条 —— 5 分钟涨 2 倍比 24 小时涨 2 倍更值得看。

### 7.5 报警频率

不做频率压制。用户明确表示"每天响一百次都可以，每个币的异动都要提醒"。
过滤层负责把噪音挡在监控之外，而不是靠事后压制报警。

## 8. 容量

10 人 × 过滤后 15–30 个币 ≈ 150–450 个币。

**实测修正（2026-08-30，`npm run bench:pump`）**：单币一轮判定
（288 根 candle × 4 窗口 × 2 基准 × 3 档位）只要 **0.112 ms**，
450 个币占 120 秒预算的 0.04%。**CPU 不是瓶颈。**

本节原先写的"175ms/币、跑满要 26–79 秒、超过轮询周期"是拿看板的
ATH 重算成本推的，而钱包引擎不做 ATH 重算 —— 它只在 288 根 candle 上
求四个窗口的极值。批量报价把这个担心整个消掉了。

真正的约束是网络：450 个币 ÷ 每次 30 个地址 = 15 次请求，
按 500ms 间隔约 7.5 秒，远在 120 秒周期内。

设计仍然保留这两条，理由不变：

- 钱包币用 DexScreener 的**批量接口**（一次最多 30 个地址）。钱包币只需要
  报价，不需要全池聚合与主池选举
- 钱包币轮询周期 2 分钟，与看板的 30 秒分开
- `tokens` 表加 `visibility` 字段（`public` | `wallet`）。某个币同时在看板和
  钱包里时，**钱包引擎让位不写 candle** —— 轮询器 30 秒一轮且做跨池校验，
  数据更好；两边都写会互相覆盖 h/l 与 liquidity_total（主池口径 vs 全池口径）

## 9. 报警触达

网页声音 + 系统通知（Notification API）。不推 Telegram。

两个浏览器层面的硬限制，设计必须正面处理：

- **不能自动出声**：必须用户先在页面上交互过。需要显式的"开启声音"开关，
  且换设备/清缓存后要重新点。未授权状态要在 UI 上显眼标出（第 4 条铁律 ——
  用户以为开着、其实没声音，是这个功能最危险的失效方式）。
- **后台标签页定时器被节流到约 1 分钟**。因此**不能用轮询拉报警**，
  要用 SSE：worker 写库，web 进程每 3 秒查一次本地 SQLite 的新报警
（本地文件读，成本可忽略），有新的就通过 SSE 推给浏览器。
  SSE 消息在后台标签页仍会及时到达，Notification 也能从后台标签页弹出。

（这个坑在 K 线图那里踩过：`requestAnimationFrame` 在非可见标签页根本不触发。）

## 10. 数据模型

```
users            (id, name UNIQUE, password_hash, created_at)
sessions         (token_hash PK, user_id, created_at, expires_at)

wallets          (id, user_id, chain, address, label, last_scanned_block,
                  last_scan_at, last_scan_error, enabled, created_at,
                  UNIQUE(user_id, chain, address))

holdings         (wallet_id, token_id, balance TEXT, decimals,
                  first_seen_at, last_seen_at, monitored, filter_reason,
                  PK(wallet_id, token_id))

pump_states      (token_id, timeframe, basis, level, state, last_fired_at,
                  PK(token_id, timeframe, basis, level))       -- 全局

pump_alerts      (id, user_id, token_id, fired_at, timeframe, basis, level,
                  multiple TEXT, price_usd TEXT, base_price_usd TEXT,
                  balance TEXT, value_usd TEXT, acked_at)      -- 每人一行
```

`tokens` 表新增：`visibility TEXT DEFAULT 'public'`。

窗口列名用 `timeframe` 而非 `window` —— `window` 是 SQLite 的关键字（窗口函数），
用它当列名每次都要加引号，迟早写漏一处。值域 `5m|1h|6h|24h` 与 `candles.timeframe` 同构。

所有价格与余额列一律 `TEXT`（十进制字符串），与项目既有约定一致 ——
让 float 既不能从入口进来，也不能从出口出去。

## 11. 界面

现有站点加一个 `/wallet` 区，跟随现有视觉规范（`src/components/TokenRow.tsx`
的层级、`src/lib/severity.ts` 的配色）。

- 未登录个人账号时显示登录/注册表单
- 钱包列表：地址、链、上次扫描时间、扫描错误（如有）
- 持仓列表：币、余额、价值、各窗口涨幅、是否在监控、未监控的原因
- 报警历史
- "开启声音"开关及其当前状态

持仓价值**显示**给本人 —— 数据不出服务器，没有隐去的必要。
